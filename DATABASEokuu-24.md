# OKU_24 — Database Specification

**Версия:** 1.0  
**База данных:** Neon PostgreSQL  
**ORM:** Prisma ORM  
**Backend:** NestJS + Node.js + TypeScript  
**Архитектура:** Monorepo + Modular Monolith

---

# 1. Общая информация

## 1.1. Назначение базы данных

База данных OKU_24 предназначена для хранения и обработки всей информации онлайн-магазина физических печатных книг и аудиокниг.

База данных должна обеспечивать:

- Хранение пользователей и их профилей.
- Управление физическими книгами.
- Управление аудиокнигами.
- Хранение категорий и жанров.
- Управление корзиной.
- Создание и обработку заказов.
- Хранение информации об оплатах.
- Управление доступом к купленным аудиокнигам.
- Хранение истории прослушивания.
- Управление избранным.
- Хранение отзывов.
- Управление уведомлениями.
- Ведение журнала административных действий.

## 1.2. Основные технологии

- PostgreSQL — основная СУБД.
- Neon — облачная платформа PostgreSQL.
- Prisma ORM — взаимодействие с базой данных.
- TypeScript — типизация.
- NestJS — серверная бизнес-логика.

---

# 2. Общие правила проектирования

1. Все основные сущности должны иметь уникальный идентификатор.
2. Для идентификаторов рекомендуется использовать UUID.
3. Для дат создания и изменения использовать `createdAt` и `updatedAt`.
4. Денежные значения хранить целыми числами в минимальных денежных единицах.
5. Для валюты использовать отдельное поле `currency`.
6. Не хранить аудиофайлы и изображения непосредственно в PostgreSQL.
7. Для медиафайлов хранить ключи и метаданные S3 Storage.
8. Использовать внешние ключи для связей между таблицами.
9. Предусмотреть индексы для часто используемых полей.
10. Использовать транзакции для операций, связанных с заказами и оплатами.
11. Не удалять финансовую историю заказов и платежей без специальных процедур.
12. Проверять права доступа на Backend, а не только на Frontend.
13. Использовать Prisma Migrations для изменения структуры базы данных.

# 3. Пользователи и авторизация

## 3.1. Таблица Users

Хранит информацию о зарегистрированных пользователях.

| Поле | Тип | Описание |
|---|---|---|
| id | UUID | Уникальный идентификатор |
| email | String | Электронная почта |
| passwordHash | String? | Хеш пароля |
| firstName | String? | Имя |
| lastName | String? | Фамилия |
| phone | String? | Номер телефона |
| avatarKey | String? | Ключ аватара в Storage |
| status | UserStatus | Статус пользователя |
| emailVerifiedAt | DateTime? | Дата подтверждения почты |
| createdAt | DateTime | Дата регистрации |
| updatedAt | DateTime | Дата обновления |

Email должен быть уникальным.

Пароль хранится исключительно в виде безопасного хеша.

## 3.2. Роли пользователей

Использовать перечисление `UserRole`:

- USER
- ADMIN

Гость не хранится в базе как пользователь. Это неавторизованный посетитель сайта.

Назначение административной роли разрешено только уполномоченным администраторам или через безопасную серверную процедуру первоначальной настройки.

## 3.3. Таблица Sessions

Хранит активные пользовательские сессии.

Поля:

- id
- userId
- tokenHash
- expiresAt
- createdAt
- revokedAt

Токены должны храниться в безопасном виде. Сессии должны поддерживать завершение и отзыв доступа.

## 3.4. Таблица Addresses

Хранит адреса пользователей.

Поля:

- id
- userId
- title
- recipientName
- phone
- country
- city
- street
- building
- apartment
- postalCode
- comment
- isDefault
- createdAt
- updatedAt

Один пользователь может иметь несколько адресов.

## 3.5. Дополнительные таблицы авторизации

Предусмотреть:

- EmailVerificationTokens — подтверждение электронной почты.
- PasswordResetTokens — восстановление пароля.

Секретные токены должны храниться в виде хешей и иметь срок действия.

# 16. Правила работы с данными

## 16.1. Удаление товаров

Удаление товаров не должно нарушать историю заказов.

Для товаров, которые уже участвовали в заказах, рекомендуется использовать архивирование или снятие с публикации вместо физического удаления.

## 16.2. Остатки физических книг

При оформлении и подтверждении заказа Backend должен проверять наличие товара.

Уменьшение складских остатков должно происходить в контролируемой транзакции, чтобы избежать продажи одного экземпляра нескольким покупателям.

## 16.3. Оплата

Все финансовые операции должны обрабатываться через Backend.

Нельзя доверять сумме, переданной Frontend. Итоговая сумма заказа должна рассчитываться сервером на основании актуальных цен и условий доставки.

## 16.4. Доступ к аудиокнигам

Доступ предоставляется только после подтверждения успешной оплаты или другого разрешённого способа получения доступа.

Проверка прав выполняется на Backend при каждом запросе защищённого аудиоконтента.

## 16.5. Транзакции

Использовать транзакции Prisma для:

- Создания заказа и его элементов.
- Подтверждения оплаты.
- Изменения складских остатков.
- Предоставления доступа к аудиокнигам.
- Отмены заказа и восстановления остатков, если это необходимо.

# 20. Итоговая архитектура базы данных

Основная СУБД: Neon PostgreSQL.

ORM: Prisma.

Хранение медиафайлов: S3 Storage.

Кэширование: Redis при необходимости.

Backend: NestJS.

База данных должна быть нормализована, безопасна, масштабируема и готова к дальнейшему расширению функциональности OKU_24.

**Главное требование:** структура базы данных должна соответствовать бизнес-логике проекта, обеспечивать целостность данных и не допускать выдачу доступа к неоплаченным товарам.
